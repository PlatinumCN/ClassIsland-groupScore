# 逻辑自检台

给「小组积分」插件的数据层与业务层跑一遍回归测试，**不需要启动 ClassIsland**，
也不依赖任何图形界面。

它不引用插件项目，而是直接把插件里那几个「纯逻辑」源文件编译进来：

- `Models/*.cs`（四张表）
- `Services/JsonStore.cs`
- `Services/ScoreStore.cs`
- `Services/ScoreService.cs`
- `Services/SettingsService.cs`
- `Actions/AddScoreActionSettings.cs`（行动设置模型；它刻意不引用 ClassIsland，
  所以能被编进来测「存进自动化配置」的序列化往返）

好处是绕开了 `ClassIsland.Core` 和 Avalonia 的窗口部分，
可以在任何装了 .NET 8 的机器上独立跑通。

## 跑一遍

```bash
cd _SelfTest
dotnet run
```

看到 `结果：84 通过 / 0 失败` 就说明逻辑没被改坏。

## 覆盖了什么

| 组 | 验证内容 |
|---|---|
| 1 | 空库首次运行会播种 4 组 + 5 个预设，且 `Seeded` 标记写入 |
| 2 | 加减分的双写一致性：记录求和 == 缓存总分；`delta=0` 与未知小组被忽略 |
| 3 | 排行榜排序、**并列名次为 1,2,2,4**、TopN 截断、今日变化、画刷可用 |
| 4 | 撤销：回退总分、删除记录、连续撤销、空记录返回 false |
| 5 | 小组 CRUD、批量导入去符号、上移重排 SortOrder、**级联删除记录与成员** |
| 6 | 持久化往返（中文不被转义、四张表都在、重载不重复播种） |
| 7 | 时间维度统计（今天 vs 上周）、乱序文件重载自愈 |
| 8 | CSV 导出：表头、汇总段、含逗号字段的引号转义 |
| 9 | 损坏 JSON 容错：不抛异常、备份留档、仍能正常播种 |
| 10 | 设置持久化与 `BallOpacity` 夹紧 |
| 11 | **静态体检**：图标码位合法性、扩展身份不重复、行动类都注册了、继承写法对不对（见下） |
| 12 | 「小组加减分」行动：设置模型默认值、**JSON 往返**（含受影响名单）、恢复语义（反向量而非删记录、快照精确回退） |

### 第 11 组：为什么值得单独拿出来说

前面 10 组都是「把代码跑起来看结果」，第 11 组不一样 ——
它**直接读插件源码**，专抓那些「编译器和运行时都不报错、但界面一定难看」的问题。

起因是真实踩到的一个坑：`[ComponentInfo]` 的图标参数填了 `"\ue9a8"`。
这个码位**是合法的**，编译通过、运行也不报错，
但它实际是 `HourglassRegular`（沙漏）而不是奖杯 ——
组件库里会显示一个沙漏，只有肉眼看界面才发现。

所以第 11 组做了四条断言：

1. **每个图标码位都必须是 ClassIsland 认识的 Fluent 图标**
   （拿本机 `ClassIsland.Core.dll` 里的 `Icons.FluentIconKind` 当码表，5332 个成员）
2. **每个图标字面量都必须在同行注释里写明图标名**，且这个名字必须和码位对得上
   —— 也就是说注释不是装饰，而是被机器校验的断言
3. **组件 GUID / 设置页 id / 行动 id 全局唯一，且每个行动类都在 `Plugin.cs` 里注册了**
   （写了行动类却忘了 `AddAction<T>`，等于白写）
4. **带设置界面的行动，继承写法必须正确**（这条是第 2 批自动化行动时加的）

第 3 条里「行动类都注册了」这条尤其有用：`AddAction<T>` 是纯注册，
漏写不会有任何编译错误，只会在「添加行动」菜单里悄悄地少一项。

第 4 条抓的是插件里**最阴**的一个坑。ClassIsland 是这样拿行动设置的：

```csharp
var settingsType = provider.GetType().BaseType?.GetGenericArguments().FirstOrDefault();
```

也就是说「行动 → 设置类型」和「设置控件 → 设置类型」这两条链都必须是**直接**继承
`ActionBase<T>` / `ActionSettingsControlBase<T>`。中间插一层自定义基类
（比如像悬浮球那四条行动共用的 `BallActionBase`）**不会报任何错**，
只会让行动设置永远是 `null`。

所以这条检查会直接从源码里把「类名 → 直接基类」的对应关系抠出来，
再拿 `Plugin.cs` 里 `AddAction<A, B>` 的实参去对：两边必须都是框架泛型基类，
而且泛型实参必须是同一个类型。

> 第 3、4 组这类检查本身都做过负向测试：故意把码位填成非法值、故意让注释名和码位不一致、
> 故意在 `AddScoreAction` 和 `ActionBase<T>` 之间插一层临时基类 ——
> 都能被准确报出来并定位到具体位置。**一条永远不会失败的检查等于没有检查。**

> 第一版第 4 条还误报过一次：它把注册代码上方注释里写的示例
> `AddAction<TAction, TSettingsControl>` 当成了真实调用。
> 修法是扫代码前先剥掉 `//` 行注释 —— 现在 `StripLineComments` 就在干这件事。

## 注意

改了插件的 `Models/` 或 `Services/` 之后请重跑一遍。
如果新增了文件、而它也需要被测试覆盖，记得在 `gs-test.csproj` 的
`<Compile Include=...>` 里加上对应的路径。

**这个目录必须留在插件项目文件夹之外**（现在放在上一级的 `_SelfTest/`）。
如果塞进 `GroupScorePlugin/` 里面，SDK 默认的 `**/*.cs` 通配会把测试代码
一起编进插件，插件就编译不过了。

第 11 组是靠「从自检台输出目录往上找 `GroupScorePlugin/` 兄弟目录」定位源码的，
所以**不要把 `_SelfTest` 和 `GroupScorePlugin` 分开搬走**。
真找不到时会打印 `[跳过]` 并让对应断言失败，不会假装通过。

另外第 11 组需要读本机 `C:\Devc++\ClassIsland\app-2.1.0.1-0\ClassIsland.Core.dll`
来当图标码表。换了 ClassIsland 安装位置的话，改一下 `Program.cs` 里的 `coreDll` 常量；
或者干脆在别处只跑第 1–10 组（把第 11 组整段删掉即可，它不依赖任何业务代码）。
