# 小组积分 · 开发文档

> 面向使用者的功能介绍与安装步骤在 [README.md](README.md)。
> 本文面向改代码的人：架构、数据表、存储层、交互流程、自检台。

- **面向版本**：ClassIsland `2.1.0.1`（实测环境，Avalonia 11.3.17 / .NET 8）
- **插件 SDK**：`ClassIsland.PluginSdk 1.7.106.2-dev-v2`

---

## 一、关于「悬浮球」这个前提

需要先讲清楚一件事：**ClassIsland 2.1 本身没有悬浮球功能**，
插件 SDK 里也没有任何 Float / Ball 相关的扩展点。
（这是查遍 `ClassIsland.Core` 的 API 文档与主程序字符串后确认的——
ClassIsland 自带的是「主界面」那个大窗，不是小控件。）

所以本插件的积分球是**自己 `new` 的一个 Avalonia 无边框置顶透明窗口**，
生命周期完全由插件管理。这一点决定了 `FloatingBallHost` 是整个项目的技术重心之一。

> `MemberScores.cs`（成员积分聚合）、`BallPlacement.cs`（悬浮球位置算术）、
> `PeriodStats.cs`（历史对比的时间切片）、`LessonRules.cs`（科目筛选与时段守门）、
> `ScorePanelStyles.cs`（面板样式归一化）、`QuickRows.cs`（平铺行尾按钮生成）、
> `RecordWriteDecision.cs`（增量落盘判定）、
> `SqliteNativeLoader.CandidatePaths`（原生库候选路径）。
> 它们最容易出错的地方恰好全是纯算术 —— 球跑到屏幕外、日期差一天、
> 名次算反、样式落进空格、按钮和分值错位 —— 抽出来之后自检台能**直接调用真代码**跑断言，
> 而不是在测试文件里把同样的 if 再抄一遍（那测的是抄写，不是逻辑）。
> 代价是：**这些文件里出现一个 Avalonia 类型，整组断言就会静默消失**，
> 所以另有一层产物级验证专门盯着这件事。

> `BallPlacement.cs` 里一个 Avalonia 类型都没有，这是**故意的**：
> 窗口定位最容易出的错（球跑到屏幕外、拔掉副屏后找不回来）全是纯算术，
> 抽出来之后自检台能直接调用真代码跑断言，而不是在测试里把同样的 if 再抄一遍。
>
> `MemberScores.cs` 同理：个人分怎么聚合、剔掉一个成员之后他那些分归谁，
> 也全是纯算术。**这个文件里一旦出现一个 Avalonia 类型，整组成员断言就会静默消失**，
> 所以产物级验证里专门有一条盯着它（见第七节）。

## 三、四张表与它们的关系

```
GROUP ──1:N──> MEMBER
  │
  └──1:N──> SCORE_RECORD <──N:1── PRESET
```

Item | 关键字段 | 职责
-----|---------|-----
`GROUP` | Id / Name / Color / SortOrder / **CachedTotal** | 小组主体，`CachedTotal` 是总分缓存
`MEMBER` | Id / GroupId / Name / SortOrder | 可选。不追溯到个人就一直是空表
`SCORE_RECORD` | Id / GroupId / MemberId? / **Delta** / Reason / PresetId? / CreatedAt | 每次加减分一条，**列表顺序即时间顺序**
`PRESET` | Id / Label / Delta / SortOrder | 快捷按钮模板

**三个重要设计决定：**

**1. 总分是缓存，不是权威。** 真正的权威是 `SCORE_RECORD`。
加一分时同时做两件事：追加一条记录、更新 `CachedTotal`。
这样「撤销」「按时间段统计」「审计谁在什么时候加的分」全都变成简单查询，
而排行榜不必每次把几千条记录重新求和。
代价是：**任何绕过 `ScoreService` 直接改 `CachedTotal` 的代码都会造成两边不一致**。

**2. 四张表放同一个数据文件里。** 一次加分要同时改两张表（记录表追加一条、
`GROUP.CachedTotal` 加一点），分成四个文件就得写多次，
中途断电就会出现「记录写了但总分没更新」的坏数据。
一个文件 + 一次事务 = 不会只写进去一半。
（最初是 JSON 整文档 + 原子替换，现在换成了 SQLite，见下一节。）

**3. 成员的个人分不缓存，每次从记录现算。**
小组分之所以敢缓存，是因为排行榜要频繁渲染；成员分只在打开成员页 / 悬浮球面板时算一次，
现算完全够快。而缓存它会带来一个实实在在的麻烦：撤销的实现是「删掉最后一条记录」，
要是成员也存了一份总分，撤销就得同时维护两份缓存 —— 又多一条能不同步的路。

由此得到一条**恒等式**，它同时也是数据完整性检查：

```
成员个人分之和  ＋  未指派到个人的分  ＝  小组总分
```

等式右边是缓存值，左边是从记录现算的。两边只要对不上，就说明有人绕过了双写。

### 数据存在哪：SQLite（附带一整套保底）

四张表是**真正的四张表**，存在 `score-data.db` 里。具体路径在设置页
「预设与设置」Tab 底部能看到，那一行同时也会显示当前实际生效的后端名字。

从旧版本升级上来的话，原来那份 `score-data.json` 会被**改名留档**成
`score-data.json.migrated-<时间戳>.bak`（不是删除）。确认新数据没问题之后可以自己删掉。

**跑起来的关键是「失败也要能用」。** 所以决定用哪个后端要过四道关卡，
任何一道过不去就自动退回 JSON：

1. **原生库能不能加载。** SQLite 的核心是 C 写的，托管包只是个壳，
   真正干活的是原生 `e_sqlite3.dll`，由 `DllImport` 在第一次开库时才去找。
   而 ClassIsland 是用自己的 `AssemblyLoadContext` 加载插件的，
   未必会把插件目录交给原生库探测 —— 那样就会在老师点「+1」的瞬间抛
   `DllNotFoundException`，编译期毫无征兆。
   所以构建脚本会把它**平铺到插件根目录**（而不是留在
   `runtimes/win-x64/native/` 里），插件启动时还会再用绝对路径主动加载一次，双保险。
2. **在这台机器上真开一次库试试。** 在临时文件上试，不碰真实数据文件，
   试完连临时文件都不会留下。
3. **数据文件读得动吗。** 损坏、被别的程序锁住、数据目录权限变了，都算读不动。
4. 四道都过了才用 SQLite。

任何一关没过，插件都会**安静地退回 JSON 继续跑**，并把原因写在设置页那行路径下面。
这是有意为之：教室里最坏的结局不是「存储格式老了」，而是「这节课的分没记上」。

**想退回旧 JSON**：删掉 `score-data.db`，再把
`score-data.json.migrated-*.bak` 改回 `score-data.json` 就行。

**落盘策略**：只有 `SCORE_RECORD` 会一直长大（一学期几千条），所以只有它做增量 ——
判断是「什么都不写 / 只追加尾部 / 整表重写」；
小组、成员、预设三张表本来就只有几十行，每次全量重写最省心。
这个判断逻辑（`RecordWriteDecision`）被特意写成不依赖任何 IO 的纯函数，
因为**它判断错了不会报错**，只会让某些记录悄悄写不进去 ——
等老师发现分数不对时往往已经过去好几节课了。
另外连接池是关掉的：开着的数据库文件会被本进程长期占住，
老师在资源管理器里连复制一份备份都做不到。

`ScoreService.CheckGroupBalance()` 就是这条等式，界面在成员页上会悄悄跑一次，
不成立时会亮一行警告。

## 四、各模块职责

**数据层**
- `JsonStore`：原子写（先写 `.tmp` 再替换）、中文不转义（否则文件里全是 `\uXXXX`）、
  文件损坏时自动备份留档并从空白开始，绝不因为一个坏文件让插件加载失败。
- `ScoreStore`：内存为主、落盘为辅。改动后延迟 1 秒才真正写盘，
  连点十次「+1」只产生一次磁盘写入；退出前强制刷盘。

**业务层**
- `ScoreService`：业务唯一入口。改完数据触发 `ScoresChanged` 事件，
  界面订阅它自动刷新，不需要任何轮询。
  成员维度的读写也全在这里（增删改名、转组、查个人分），
  其中 `DeleteMember` 走的是「把记录孤儿化」而不是「删记录」（下一节解释）。
- `MemberScores`：成员积分的纯算术。个人分聚合、并列名次、未指派分的定义、
  删成员时的记录处理、组内顺序归一化，都是静态纯函数。
  **不引用任何 Avalonia / ClassIsland 类型**，自检台才能直接调它。
- `PeriodStats`：历史对比的纯算术。周期切分（自然周 / 自然月、可变周起始）、
  左闭右开区间判定、期内净增、截至某时刻的累计分、两套名次。
  同样**不引用任何 UI 类型**；服务层只负责把数据喂给它，`ScoreService` 里一行日期算术都没有。
- `PeriodComparison`：对比结果的模型 —— 区间、总览、每一行。
  行里直接持有 `Group` 引用（名字改了表里立刻跟着变，不抄一份）。
- `FloatingBallHost`：订阅 `ILessonsService` 的 `OnClass` / `OnBreakingTime` / `OnAfterSchool`，
  实现自动弹出与收起；并把所有界面操作切回 UI 线程。
- `SettingsService`：只读写 `settings.json`。**刻意不碰积分数据**——
  如果它顺手 `new` 一个 `ScoreStore`，就会产生第二份内存数据，最终互相覆盖。

**表现层**
- `ScoreBoardComponent`：主界面只读展示。用 `Loaded` / `Unloaded` 订阅与退订事件。
- `FloatingBallWindow`：一个窗口两种形态，靠 `SizeToContent` 自动跟随内容尺寸。
  成员下拉是在这里接上的（课上最常见的场景就是「张三回答对了」）。
- `GroupScoreSettingsPage`：唯一的管理台，五个标签页
  （小组管理 / 小组成员 / 积分操作 / 历史对比 / 预设与设置）。

## 五、关键交互流程

### 流程 1：上课铃响 → 积分球出现（可以只对指定科目）

```
ClassIsland 主计时器判定进入上课
        │
        ▼
ILessonsService.OnClass 事件
        │
        ▼
FloatingBallHost.HandleOnClass
        │
        │  LessonRules.ShouldAutoShow(...)：
        │    ├─ 「上课自动弹出」没开？          → 不弹
        │    ├─ 科目白名单没启用？              → 弹（老行为，任何课都弹）
        │    ├─ 白名单是空的？                  → 不弹
        │    ├─ 当前没有科目（自习 / 课间）？    → 不弹
        │    └─ 当前科目在白名单里？            → 弹，否则不弹
        ▼
Dispatcher.UIThread.Post(...)     ← 课程事件不保证在 UI 线程，必须切回去
        │
        ▼
首次调用 → new FloatingBallWindow（无边框 + 置顶 + 不进任务栏 + 透明）
        │
        ▼
SizeChanged → ApplyPosition() → 摆到该在的地方
                                （拖过就用记住的位置，没拖过就按设置的角落）
```

科目名从哪来：`ILessonsService` 的 `CurrentSubject`（这个属性实际声明在它的父接口
`IPublicLessonsService` 上，在 `ClassIsland.Shared.IPC` 里 —— 直接反射 `ILessonsService`
会以为它不存在）。框架给「没有课 / 课间」准备的是 `Subject.Empty` / `Subject.Breaking`
两个占位对象，一律当作「没有科目」。

判定本身写在 `LessonRules.ShouldAutoShow` 里，**一个 ClassIsland 类型都不引**，
所以自检台能对着同一套规则真跑（第 18.1 组）。

### 流程 2：老师点击积分球 → 展开操作面板

```
单击圆球（Tapped）
        │
        ▼
SetExpanded(true)
   ├─ 记下球此刻的位置（_expandAnchor）
   ├─ 圆球隐藏、面板显示
   ├─ ApplyPanelStyle()  按设置决定显示哪个区域（逐个选择 / 全部展开）
   ├─ BuildPresets()     按当前预设项动态生成快捷按钮
   ├─ RefreshGroups()    刷新小组下拉（用 Id 签名短路，避免刷掉老师的选择）
   └─ RefreshRank()      拉取前 N 名
        │
        ▼
窗口 SizeToContent 自动从 64×64 变成 340 宽
        │
        ▼
SizeChanged → ApplyPosition()
   展开态：以球的位置为锚点，往右下「长」出来（贴到屏幕边时自动收进去）
   收起态：按「拖动记忆 / 停靠角落」重新算
```

**为什么要记这个锚点**：面板比球宽得多。要是展开时还按设置重算一遍位置，
球会先跳回屏幕角落、面板再从那儿冒出来 —— 看起来像被谁挪了一下。
记住球在哪儿、让面板从那儿长出来，这个动作才连得上。

### 加分面板的两种样式

面板右上角有个切换按钮（写的是**点一下会切到哪个样式**），设置页里也能改默认值。
两种样式不是「新旧版本」，是给两种不同场合准备的：

| | 逐个选择（默认） | 全部展开 |
|---|---|---|
| 长什么样 | 下拉框挑小组 → 下方一排预设按钮 | 每个小组各占一行，行尾直接就是按钮 |
| 加分要几步 | 2 步（先选组，再点按钮） | 1 步（点哪行的按钮就给哪组加） |
| 适合 | 小组多、要指到具体学生头上 | 课上最高频的「看见哪组好就给那组加一分」 |
| 行尾按钮是什么 | 全部预设项 | 预设项（短标签 `+2`/`-1`，悬停能看到完整原因） |

几个刻意的决定：

- **全部展开也走预设项**，不是简单的 ±1。预设承载着「原因」——
  「张三答对了」和「张三 +1」在期末复盘时是完全不同的两回事。
  一个预设都没配的时候才退化成 ±1 兜底，免得老师面对一排点了没意义的行。
- **行尾按钮只有数字**（`+2`），完整原因放在悬停提示里。340 宽的面板一行要挤下三四个按钮，
  塞整句预设名会撑爆。颜色按国内习惯：加分红、扣分绿。
- **全部展开会自动收掉下方的迷你排行榜** —— 每行本来就带着分数，再挂一遍是重复信息。
- **样式选择会写进设置**，下次打开还是这个样式；但按钮始终写的是「能切到哪」，
  不是「现在是什么」，不用猜当前状态。

### 流程 3：加一次分

```
点「回答正确 +2」
        │
        ▼
ScoreService.AddScore(groupId, +2, "回答正确", presetId)
   ├─ 追加一条 ScoreRecord
   ├─ group.CachedTotal += 2       ← 双写，同步完成
   └─ ScoreStore.MarkDirty()       ← 安排 1 秒后落盘
        │
        ▼
ScoresChanged 事件
        │
        ├──> ScoreBoardComponent   主界面积分榜立即重排
        ├──> FloatingBallWindow    面板里的迷你榜立即刷新
        └──> 设置页                 记录列表立即刷新
```

界面是「整表重绑」而不是增量更新：一次加分会让名次整体变化，
增量更新的复杂度远高于收益，课堂规模的数据量重绑一次几乎无感。

### 流程 4：撤销上一步

```
点「撤销上一步」
        │
        ▼
ScoreService.UndoLast()
   ├─ 取记录列表的最后一条（列表顺序 = 时间顺序，不需要额外的撤销栈）
   ├─ 删除它
   └─ group.CachedTotal -= 那次 Delta
        │
        ▼
ScoresChanged → 所有界面刷新
```

连点多次就是连续撤销。记录表本身就是栈，不必再维护一份状态。

### 流程 5：按住拖动换位置（收起态和展开态都能拖）

```
PointerPressed（按下）
   ├─ 命中按钮 / 下拉框 / 输入框 → 不启动拖动，让控件自己处理这一下
   └─ 命中空白处（或圆球）      → 记下按下点 + 窗口左上角 + 捕获指针
        │
        ▼
PointerMoved（移动）         位移 < 4 像素 → 当手抖，什么都不做
        │
        ├─ 超过阈值 → _dragMoved = true
        │              位置 = 按下时的位置 + 累计位移，再钳进屏幕
        │              （始终从按下点算，所以拖到边界后指针往回收能立刻跟回来）
        ▼
PointerReleased（松开）      只有这时才写设置 → 触发一次落盘
        │                    （写在 Moved 里的话，拖一次要写几十遍磁盘）
        ▼
PluginSettings.BallX / BallY 被赋值 → settings.json 落盘
        │
        ▼
下次上课球就出现在你拖到的那个地方
```

四个细节值得说明：

1. **展开之后也能拖**。这是最初版本的缺陷：圆球挂了指针事件，面板一个都没挂，
   而展开时圆球已经被藏起来（`IsVisible = false`）—— 于是面板一展开，窗口唯一能按住的地方
   恰好没有手势，位置就锁死了，只剩「收起」能做。现在两块挂的是同一套手势。
2. **两条入口共用同一个 `BeginDrag`**，不是各写一份。各写一份的话，改一处漏一处，
   而漏掉的那一处表现是「拖着不走」，通常要等真在那个状态下才发现。
3. **面板内会避开按钮 / 下拉框 / 输入框**。整块面板都可以拖，但按住按钮时不能启动窗口拖动 ——
   否则控件再也收不到一次完整的点击，表现是「按钮点不响」，很难联想到是拖动抢走了它。
   判定方式是从命中的元素往上找，撞到窗口为止。
4. **点击和拖动只能靠位移阈值区分**。球只有 64 像素，老师的手一定会抖；
   如果看到 Moved 就搬窗口，那「想展开面板」会变成「球被挪了一像素」。
   所以小于 4 像素的位移仍然按点击处理，正常走 `Tapped` 展开面板。
   （阈值指的是 **4 个逻辑像素**，实际比较时乘了 `RenderScaling`。）

5. **位移必须取「指针的屏幕坐标」，尺寸必须换算成物理像素** —— 这一条是 2026-10-17 实测出来的
   两个真 bug，都只在非 100% 缩放、或者拖得比较快的时候才显形：

   - 事件的 `GetPosition` 给的是**相对窗口客户区**的坐标。窗口在拖动过程中自己也在动，
     同一个物理位置在客户区坐标系里的读数会跟着窗口一起变，两次事件相减出来的位移
     会被窗口自身的位移抵消掉一部分。鼠标动得越快抵消得越多，贴到屏幕边被钳住时抵消 100%
     —— 表现是「球越拖越跟不上手，最后粘在边上不动」。所以位移一律走
     `BallPlacement.PointerOnScreen` 换成**绝对屏幕坐标**再相减。
     （`Window.Position` 的 getter 是 `GetWindowRect`，读的就是此刻窗口的真实位置，没有缓存滞后。）
   - `ClientSize` / `Bounds` 是**逻辑单位**（Win32 后端里就是 `GetClientRect` 的结果
     除以 `RenderScaling`），而 `Window.Position`、`Screens.WorkingArea` 全是物理像素。
     两边混着算，150% 缩放下 340 宽的面板会被当成占 340 个像素（实际 510），
     于是球贴边时露出一大截在屏幕外。所以尺寸一律过 `BallPlacement.ToPhysicalSize`。

   这两条都有自检台断言盯着（第 11.6b 组扫源码 + 第 14.4b 组算数值），改回去会立刻 FAIL。

另外两条：

- **必须捕获指针**（`e.Pointer.Capture(source)`）。不捕获的话指针一滑出被按住的那一块，
  `Moved` 事件就全丢了，表现是「跟到半路卡住」。松开时记得 `Capture(null)` 还回去。
- **记忆位置每次都要重新钳制**。把副屏拔掉之后，settings.json 里留下的坐标
  可能落在屏幕外；`BallPlacement.Resolve` 会把它拉回主屏可见区域，
  而不是让球凭空消失。

「恢复默认位置」在 设置页 → 预设与设置 → 悬浮球；点它会清掉拖动记忆并让球立刻归位。
改「停靠位置」也会顺带清掉拖动记忆 —— 否则会出现「选了右上角，球却还停在自己拖出来的地方」。

### 流程 6：给某个学生加分（成员维度）

```
悬浮球面板：选小组 → 选成员（默认「（不指名，只记小组）」）→ 点「回答正确 +2」
        │
        ▼
ScoreService.AddScore(groupId, +2, "回答正确", presetId, memberId)
   ├─ 校验 memberId 的归属（不属于这个组就降级为不指名，分照记 —— 见下）
   ├─ 追加一条带 MemberId 的 ScoreRecord
   └─ group.CachedTotal += 2        ← 个人分和小组分是「同一笔分」，不是两笔
        │
        ▼
个人分不是存在成员身上的，而是每次从记录现算：
   GetMemberTotal(memberId) = 该成员名下所有记录的 Delta 之和
```

**为什么删掉一个学生，他的分不会跟着消失。** 这是成员维度里最反直觉的一点：

```
删除成员「张三」（他名下 1 条 +5 的记录）
        │
        ▼
MemberScores.Orphanize(records, 张三.Id)
   └─ 只把那条记录的 MemberId 清空 —— 记录本身留着
        │
        ▼
小组总分不变（那 +5 依然算在组头上）
        │
        └─> 它从「张三的分」变成「未指派到个人的分」
```

理由是：删掉一个学生不等于他挣的那些分没发生过，小组总分不该因为删人不认账。
反过来，要是连带删记录，就得同时把小组的 `CachedTotal` 减回去 ——
「删个人」就变成了「改全组分数」，语义和风险都更重。

注意这跟**删小组**不一样：删小组时归属对象整个不存在了，它的记录只能一起删。

**「跨组的 memberId」也不会让分丢掉。** `AddScore` 发现 memberId 指向的成员
不存在、或者不在这个组里，就把它降级成「只记到小组一级」，而不是拒绝整笔操作 ——
老师按下按钮就期待分数进去了，宁可归属粗略，也不能让分凭空消失。

界面上的下拉都是按组过滤过的，所以这条校验只在传参写错时才会真的生效。

### 流程 7：看「本周比上周」（历史对比）

```
设置页 → 历史对比 → 选「本周 vs 上周」或「本月 vs 上月」
        │
        ▼
ScoreService.GetPeriodComparison(kind, 设置里的周起始)
   └─ 只做一件事：把真数据喂给 PeriodStats.Compare(...)
        │
        ▼
PeriodStats（纯函数，自检台里真跑）
   ├─ Of(now)          → 本期区间 [起点, 终点)
   ├─ PreviousOf(now)  → 上一期区间，末端正好接上本期起点
   ├─ TotalsByGroup    → 每组的「本期净增 / 上期净增」
   ├─ CumulativeByGroup→ 每组「期末累计 / 上期末累计」
   └─ RankByValue      → 两套名次（按期内得分、按期末累计）
        │
        ▼
表：名次 │ 小组 │ 本期 │ 上期 │ 相比 │ 累计 │ 名次变化
```

**为什么区间是左闭右开 `[起, 止)`, 而不是两头都闭。**
相邻两期的边界上必然同时存在两条记录（周日晚 23:59:59 和周一 00:00:00）。
两头都闭的话，边界那一瞬间的记录要么被两边各算一次、要么被两边都漏掉 ——
取决于你怎么拼。左闭右开天然严丝合缝：**上一期的终点就是这一期的起点**，
不重不漏。这不是洁癖，是账本的正确性。

**「上期」是上一个自然周期，不是「往前推 7 天」。**
老师说的是「这周比上周」，而周三那天往回推 7 天得到的是上周三 ——
那个 7 天窗口横跨两个自然周，比出来的数谁也对不上。

**月末往回找一个月，必须先归到月首再减。**
`3月31日.AddMonths(-1)` 会被截断成 `2月28日`，得到一个从**月中**开始的残缺区间，
而且它看起来还挺合理。所以规则是「取月首 → 减一个月」，
月首减月永远不会溢出。（自检台里有一条专门盯这个的断言，报错时直接打出 `2026-02-28`。）

**「名次变化」是拿期末累计分算的，不是拿期内得分算的。**
老师最想知道的是「格局有没有变」—— 也就是谁反超了谁。
这需要「上周这个时候各组多少分」，而 `CachedTotal` 只有**现在**这一个值，
拿它减一减是算不出历史名次的。所以 `PeriodStats` 会直接
「把截至某个时刻之前的记录全部加起来」，得到那个时刻的累计分。

**符号约定在模型里就定死了，别处不要另立一套：**
`相比 > 0` 表示比上期多得了分；`名次变化 > 0` 表示名次**前进**。
两个字段「正数都是好事」，界面才不会把箭头画反。

**「一周从周几开始」只是个「怎么看」的参数。**
改它不会动任何一条记录 —— 上周的区间会平移，表里的数字跟着变，但总分一分不差。
默认周一（国内课表习惯），设置页可以改成周日。
自检台里有一条断言专门证明这件事：同一条 10-11（周日）的记录，
按周一为起点算属于「上周」，按周日为起点算属于「本周」，而两种口径下的
**期末累计完全相同**。

### 流程 8：加分只在上课时（可选）

```
老师点「回答正确 +2」
        │
        ▼
ScoreService.AddScore(...)     ← 全部 7 个调用点唯一的入口
        │
        ▼
SafeAccess() 取一份时段快照（纯数据，三个 bool）
        │
        │  LessonRules.CanAddScore(...)：
        │    ├─ 「只在上课时加分」没开？   → 放行
        │    ├─ 课表不可用？              → 放行（原因见下）
        │    └─ 正在上课？                → 放行，否则拦下
        ▼
被拦下：不写记录、不动缓存总分，留下 LastBlockedReason 并发出 ScoreBlocked 事件
        │
        ▼
悬浮球面板状态栏 / 设置页两个状态行显示「现在不在上课时间，已按设置禁止加分」
```

**为什么「课表不可用就放行」**：老师完全可能只想要个计分器，从没在 ClassIsland 里配过课表。
那种情况下 `CurrentState` 会长期停在「放学后」，照着卡就等于把插件变成点不动的砖头。
宁可放开，也不能让一个辅助功能反过来把老师的手脚捆住。
（相同态度贯穿全插件：宿主服务读崩了也当作「不限制」。）

**为什么守门放在 `ScoreService` 而不是各个界面**：加分有 7 个调用点
（自动化行动 1 处、悬浮球面板 2 处、设置页 4 处）。在唯一入口拦一句就全覆盖了，
将来再加调用点也不会漏。自检台第 18.5 组还会**扫源码**要求每个 `AddScore` 调用点
都必须检查返回值 —— 因为被拒时返回 `false`，任何「不看返回值、照样显示已记」的地方
都是在骗老师。

### 那为什么成员分加起来常常比小组总分少？

因为它们本来就不是一回事。`SCORE_RECORD.MemberId` 允许为空，
代表这笔分是**按组**记的（「全组作业优秀」「全班纪律扣分」），它不属于任何个人。

```
第一小组 10 分  =  张三 5   ＋   李四 3   ＋   未指派 2
                    └── 指名到人的记录 ──┘      └─ 按组记的记录 ─┘
```

成员页底部会把这笔账明写出来（`分账：成员分合计 5 ＋ 未指派到个人 2 ＝ 组总分 10`），
就是因为不写清楚的话，老师很容易以为软件算错了。

而这条等式同时是个**数据完整性检查**：右边是缓存的总分，左边是从记录现算的。
两边对不上，就说明有代码绕过 `ScoreService` 的「写记录 + 改缓存」双写了。
成员页会悄悄跑一次 `CheckGroupBalance`，不成立时亮一行警告。

## 六、用「自动化」编排积分与积分球

除了插件内置的「上课弹出、下课收起」，积分球的显示时机也可以完全交给
ClassIsland 自带的**自动化**来编排。插件一共注册了**五条行动**和**一个触发器**，
在「应用设置 → 自动化 → 添加行动」里能看到一个**「小组积分」分组**：

| 行动 | ID | 做什么 | 撤销时 |
|---|---|---|---|
| 显示积分球 | `bojinxia.groupScore.ball.show` | 以收起的圆球状态出现 | 隐藏 |
| 隐藏积分球 | `bojinxia.groupScore.ball.hide` | 整个藏起来（窗口还在，再显示很快） | 显示 |
| 切换积分球显示 | `bojinxia.groupScore.ball.toggle` | 显示 ⇄ 隐藏 | 再次切换（自逆） |
| 展开积分球面板 | `bojinxia.groupScore.ball.expand` | 跳过点击，直接开面板 | 收起为圆球 |

四条行动都重写了 `OnRevert`，所以注册时会被 ClassIsland **自动标记为「可恢复」**。
于是最省事的用法是：

```
触发器「上课」 ──> 行动「显示积分球」 ✔ 勾上「可恢复」
                          │
                          └─ 下课时 ClassIsland 自动执行反向操作 → 隐藏
```

**只配一条行动，就同时得到了「上课出现」和「下课收走」。**

### ⚠️ 一个必须先处理的冲突

插件的「上课时自动弹出积分球 / 下课自动收起」和自动化**是两套独立机制**。
如果两个都开着，自动化刚把球藏起来、下一节课内置逻辑又把它弹回来，就会互相打架。

**用自动化之前，请到「插件 → 小组积分 → 预设与设置」把这两个勾去掉。**
设置页里也写了同样的提示。

### 为什么这里的撤销是「无状态」的

ClassIsland 每次运行行动都会从 DI 重新取一个行动实例
（`ActionBase.GetInstance` 内部就是 `GetKeyedService`，而行动是按瞬态注册的），
也就是说**「执行」和之后的「撤销」很可能不是同一个对象**。

所以这四条行动里找不到任何「记住上一次状态」的字段 ——
它们的撤销只依赖当前的可见性，行为是确定的。

> 这条限制有实际后果：想做「记录旧状态、撤销时精确还原」的行动，
> **用字段是走不通的**。得把旧状态写进 `ActionItem.Settings`
> （`OnInvoke` 里写、`OnRevert` 里读），才能跨实例传递。
>
> 下一节的「小组加减分」就是这条规矩的正面例子。

### 带设置界面的行动：小组加减分

上面四条是「开了就完事」的行动。还有一条不一样：

| 行动 | ID | 做什么 |
|---|---|---|
| 小组加减分 | `bojinxia.groupScore.addScore` | 给某个小组（或全部小组）加 / 减指定分值，并写入一条积分记录 |

它在「添加行动」菜单里选中后会**弹出设置面板**，可以配三件事：

- **作用对象**：某一个小组，或者「全部小组」
- **分值**：正数加分、负数扣分
- **原因**：写进积分记录里的文字

设置存在**自动化配置本身**里（`ActionItem.Settings`），不是存在插件的数据文件里。
所以同一条行动可以摆多份、各配各的 —— 比如「纪律 -1」和「回答正确 +2」各来一条。
行动在列表里显示的名字也会跟着变成 `小组加减分　+2 · 全部小组`，一排相似的行动不会认错。

目标小组如果被删掉了，执行时按「**跳过**」处理：教室里跑着的自动化不该因为一个被删掉的组整天报错。

**恢复的语义和「撤销上一步」不一样，这点必须说清楚。**

| | 撤销上一步（面板里的按钮） | 自动化行动恢复 |
|---|---|---|
| 做法 | **删掉**最后一条记录，并反向修正总分 | **记一条反向量**（原因写成 `撤销：原原因`） |
| 为什么 | 语义就是「我刚才点错了」 | 执行和恢复之间，老师很可能自己又手动加过分，删最后一条会删错人 |

而且恢复是**精确**的：执行时会把「这次动了哪些小组」记进行动设置，
恢复时照那份名单回退。执行时班里有 4 个组、恢复前老师新建了第 5 个组 —— 第 5 个不会被误扣。

这就是「撤销必须无状态」这条规矩的落地方式：
状态不放在 C# 字段里（放不住，执行和恢复很可能不是同一个对象），
而是放进会被持久化的 `ActionItem.Settings`。

一个最省事的用法：

```
触发器「上课」 ──> 行动「小组加减分」（+1 分，全部小组）✔ 可恢复
                          │
                          └─ 下课铃响 → ClassIsland 自动恢复 → 全班 -1
```

⚠️ 只重写了 `OnRevert` 还不够，还要在自动化里**勾上「可恢复」**，
ClassIsland 才会在触发器恢复时调用它。
（`ActionInfo.IsRevertable` 这个元数据你不用手写：插件注册时它会自动检测
「本类有没有重写 `OnRevert`」并置位。）

### 带设置界面的触发器：小组积分达到阈值

行动是「让 ClassIsland 去做事」，触发器是「什么时候去做」。插件注册了一个触发器：

| 触发器 | ID | 什么时候触发 |
|---|---|---|
| 小组积分达到阈值 | `bojinxia.groupScore.trigger.threshold` | 某个小组（或任意小组）的积分跨过设定的分数线 |

在「添加触发器」里选中它同样会**弹出设置面板**，配三件事：

- **盯着哪个小组**：某一个小组，或者「任意小组」（有一个够线就算）
- **条件**：达到或超过 / 掉到（含）以下
- **阈值分数线**：整数

配上「小组加减分」行动就是一个闭环：

```
触发器「小组积分达到阈值」(第 3 小组 ≥ 20) ──> 行动「小组加减分」(+2，第 3 小组，原因「小组夺冠」)
```

第 3 小组冲到 20 分的那一刻自动再奖 2 分。

**它只在「刚刚跨过去」的那一瞬间触发一次**，这点很关键。
ClassIsland 的触发器是电平式的 —— 调一次 `Trigger()` 就跑一遍行动集。
而「第 3 组已经 20 分了」这个事实在老师之后的**每一次加分里依然成立**，
要是每次都触发，庆祝音效会一直响到老师把插件删掉。

所以判定被拆成两半，两半都不依赖 ClassIsland，都能在自检台里真跑一遍：

| 文件 | 管什么 | 典型断言 |
|---|---|---|
| `GroupScoreThresholdRule.cs` | 现在够不够线 | 指定组不存在 → 不满足；正好等于阈值 → 满足；未知枚举值 → 按「达到或超过」兜底 |
| `ThresholdEdgeDetector.cs` | 是不是**刚刚**跨过去 | 连续喂三次「满足」只出一次 `Raised`；`Prime` 装填基线不产生事件 |

工作流**刚加载**时也会 `Prime` 一次：如果加载那一刻某个组早就超线了，
那是上一节课的功劳，不该在这一刻补放一遍庆祝音效。

反过来，掉回线下面时调 `TriggerRevert()` —— 同样需要行动集勾上「可恢复」才会真的恢复。

⚠️ **触发器在列表里显示的名字固定是「小组积分达到阈值」，不会带上参数。**
这跟行动不一样：`ActionSettingsControlBase` 有 `ChangeActionName()`，
但 ClassIsland 2.1 的 `TriggerSettingsControlBase` **没有**对应的改名方法，
`TriggerSettings` 里也没有存名字的字段。配了好几条阈值触发器时，
在自动化列表里只能靠展开设置面板来分辨。

## 八、已知限制

- **科目白名单是靠「科目名」对号入座的**。白名单里存的就是课表里显示的名字（如「语文」）。
  如果你后来在 ClassIsland 里把科目改了名（「语文」→「语文与阅读」），
  白名单里那条就对不上了，这门课不会再自动弹球。
  设置页会把这类「课表中已无此科目」的旧条目也画出来（名字后面带后缀），去掉重勾即可 ——
  特意这么做，是为了不让白名单里压着几个看不见的旧名字、球死活不弹而屏幕上毫无线索。
- **「只在上课时加分」也会拦住自动化的「恢复」**。自动化行动的恢复不是删记录，
  而是再记一笔反向量（见第六节），所以它同样受时段限制。
  好处是规则统一、不留「下课后还能通过自动化扣分」的口子；
  代价是老师想在下课后撤销一次自动化，得先去设置页把开关关掉。
  **「撤销上一步」按钮不受影响** —— `UndoLast` 走的是
  `Data.ScoreRecords.RemoveAt`（删记录本身），不经过 `AddScore`，所以任何时间都能用。
- **仅 Windows**。积分球用到透明置顶窗口，其他平台未做验证。
- **单机**。数据只存本机，本版不做跨机器同步。
- **拖动积分球这套手势没有在真机上跑过**。位置算术（角落解算、边界钳制、半个坐标、
  屏幕外记忆拉回）全是纯函数，自检台里跑得很透，编译产物也反射核对过；
  但「按下→移动→松开」的指针捕获、Avalonia 到底会不会在拖动之后额外补一个 `Tapped`
  （我用 `_dragMoved` 挡了，但没实测过这个交互），只有在真实 ClassIsland 里拖一次才算验证完。
  展开态那一路还多一层没验的东西：**面板上按住按钮时到底会不会被判成窗口拖动**。
  代码里做了双重保险（`IsInteractiveSource` 主动判断 + 按钮自己会吃掉 `PointerPressed`），
  但「按住按钮时点得响、按住面板空白处拖得动」这两件事都只有真机能确认。
- **拖动只认主屏**。`ApplyPosition` 取的是 `Screens.Primary` 的工作区，
  多屏环境下球拖到副屏之后，重启可能会被拉回主屏。按屏幕记忆位置是后续可做的事。
- **组件级设置未启用**。显示条数由插件设置页统一控制。
  因为 ClassIsland 的组件设置是「每个摆放实例相互独立」的，
  主界面上放两个积分榜组件就会出现两套互相矛盾的配置。
- **SQLite 后端没有在真机上跑过。** 原生库的加载做了两层保底
  （构建时平铺到插件根目录 + 启动时再用绝对路径主动加载一次），
  平铺这条路也在自检台里真跑过 —— 开库、建表、事务、中文读写、负分、
  增量写、迁移、回落，全部正常。
  但「ClassIsland 自己的 `AssemblyLoadContext` 认不认这个平铺的 dll」这件事，
  只有在真实 ClassIsland 里点一次「+1」才算验证完。
  好消息是即使它不认，插件也只会安静地退回 JSON，功能一点不受影响
  （只是设置页那行会多一句说明）。
- **`score-data.db` 目前没有被任何外部工具验证过。** 它是标准 SQLite 格式，
  理论上可以用 DB Browser 之类的工具直接打开查看，但没实测过。
- **JSON 后端仍然保留着**，它是 SQLite 不可用时的落脚点，不是过时的旧代码 ——
  改 `JsonStore` 的时候请把它当正式代码对待。同理，**不要删那个
  `score-data.json.migrated-*.bak`**，除非你确认新库里的数据是对的。
- **一次落盘仍然是「整份数据同步下去」**（内存才是运行时的真相），
  SQLite 换来的主要是事务性与「记录表不必每次重写」，
  而不是「查询变快了」—— 排行榜读的一直是内存里的缓存总分。
- **组件 GUID 不要改**。`ScoreBoardComponent` 上的
  `[ComponentInfo("6F2A5C81-...")]` 是组件的身份。
  改掉它，老师已摆好的位置都会失效。真要改必须加 `[MigrateFrom]` 做迁移。
- **行动的窗口路径没有在真机上跑过**。四条自动化行动编译通过、
  撤销语义是按 ClassIsland 源码里的实例生命周期推导出来的（确定），
  但「创建透明置顶窗口」这条链路仍需在真实 ClassIsland 里实跑一次才算验证完。
- **「小组加减分」行动同样没有在真机上跑过**。设置面板
  （`ActionSettingsControlBase<T>` 那套写法）、设置落盘（`ActionItem.Settings` 往返）、
  恢复语义，都只做到「编译通过 + 静态/逻辑自检通过」；
  「点开抽屉 → 改设置 → 保存 → 触发一次 → 再恢复」这条全链路还没在真实 ClassIsland 里实跑。
- **触发器也没在真机上跑过**。判定逻辑和边沿检测是纯函数，自检台里跑得很透；
  「加载工作流 → 触发设置注入 → 加一次分 → 行动执行」这条链路是从 ClassIsland
  源码（`AutomationService.ActivateTrigger` / `LoadTrigger`）读出来的，编译产物也反射核对过，
  但仍然没有在真实 ClassIsland 里点一次。
  另外**触发器实例是被 `TriggerSettings.TriggerInstance` 长期持有的**，
  所以这里可以用字段记状态 —— 跟行动那条「字段存不住东西」的规矩相反，别搞混。
- **行动 ID / 触发器 ID 一旦发布不要改**。老师和自动化配置里存的是 ID 字符串，
  改了等于把别人已经配好的工作流弄断。（改显示名则没有影响。）
- **成员页与悬浮球的成员下拉也没在真机上跑过**。聚合、名次、删成员语义、转组的
  「分数跟着人走」全在自检台里跑过真代码，但「点下拉 → 选人 → 加分 → 列表刷新」
  这条界面链路只有编译保证。
- **两个下拉框并排在无边框透明窗口里**还没有实测。「逐个选择」样式下有「小组」和「成员」
  两个 ComboBox，它们的下拉弹层在 `SizeToContent` + 透明置顶的窗口里表现如何，
  只有真实运行才知道。（原有的小组下拉本来就有同样的不确定，现在多了一个。）
  「全部展开」样式下没有下拉框，不受这条影响。
- **加分面板的样式切换没在真机上跑过**。样式归一化、平铺按钮的生成与兜底、
  设置往返、界面接线全在自检台里跑过真代码 + 静态体检，但
  「点面板右上角切样式 → 行画出来 → 点行尾按钮加分 → 那一行数字跟着变」
  这条链路只有编译保证。另外 **行尾按钮的数量跟预设项数量一致**，
  预设项配到七八个的话每行会挤得很满（没有做「只显示前 N 个」的截断，是有意的：
  截断会让老师以为某个预设没生效）。
- **成员页的「转到其他组」只有一层防护**。转组会同步搬走他名下的记录和两个组的总分，
  逻辑在自检台里验过（转完两组都平衡），但界面上没有二次确认，
  点错了只能靠再转回来。
- **历史对比页没在真机上跑过**。时间切片、净增、累计、名次全是纯函数，
  自检台里跑得很透（含跨月周、月末截断、半开区间边界、换周起始口径），
  但「切 Tab → 换周期 → 表里的数字跟着变」这条界面链路只有编译保证。
- **历史数字会随撤销而变**。「撤销上一步」的实现是**删掉最后一条记录**，
  所以撤销之后「上周 +16 分」可能会变成「+14 分」。这是取舍不是 bug：
  记录表本身就是唯一事实来源，历史由它派生，删了记录历史自然跟着变。
  真要做「历史快照」就得另存一份期末值，那又多一条能不同步的路。
- **周期口径依赖本机时间**。切片用的是本地时区的时间；
  系统时间被改过（比如假期把日期调回去），或跨时区使用，都会让周期归属发生变化。

## 九、后续可以做什么

- 按屏幕记忆悬浮球位置（当前只按主屏钳制，多屏下拖到副屏会被拉回）
- 成员维度的排行榜组件（把`MemberScoreItem`做成主界面可摆的组件，
  现在只有设置页和悬浮球面板能看到个人分）
- 批量导入成员（小组能一行一个地批量建，成员目前只能一个个加）
- 历史对比导出成图 / 追加到 CSV 导出里
- 历史对比支持「自定义起止日期」和「按周期滚动的趋势线」
  （切分逻辑已经参数化成 `PeriodStats.Of / PreviousOf`，加一档不难）
- 更多触发器：比如「某个组被扣分」「一节课内涨了 N 分」。
  扩展点已经验证可用（`AddTrigger<TTrigger>` / `AddTrigger<TTrigger, TSettings>`）；
  再写一个时记住两条规矩：**扩展类与设置控件类都必须直接继承框架泛型基类**，
  以及**有设置就必须同时注册设置控件**（没有设置控件，框架连设置对象都不注入）。
- 数据库结构升级机制。`SchemaVersion` 已经写进 `meta` 表了，但还没有真正的版本迁移步骤；
  将来给某张表加字段时需要一个「把 v1 的库升到 v2」的流程
  （现在只有 `CREATE TABLE IF NOT EXISTS`，**已有表缺列是不会自动补的**，
  这正好是加字段时最容易踩的坑）
- 一键导出 / 导入数据备份（现在得自己去数据目录复制 `score-data.db`）
